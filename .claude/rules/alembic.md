# Alembic Migrations

Schema migrations driven by Alembic against the same `Base.metadata` the app uses at runtime. `env.py` wires the app's metadata and overrides the connection URL from `POSTGRES_URL` so migrations target whichever database the app is configured for.

## Design intent

- `env.py` imports `app.database.models` and sets `target_metadata = Base.metadata`. Adding a new model means importing it (directly or transitively) before autogenerate runs, otherwise it won't appear in the diff.
- The connection URL comes from `app.constants.POSTGRES_URL` via `config.set_main_option('sqlalchemy.url', ...)`. `alembic.ini`'s URL field is intentionally left unset.

## Patterns

- Generate a migration:
  - `alembic revision --autogenerate -m "<message>"`
- Apply / roll back:
  - `alembic upgrade head` / `alembic downgrade -1`
- Tests run `command.upgrade(cfg, "head")` from a session-scoped fixture in `tests/conftest.py` — keep that path working.

## Conventions

- Revision files live under `alembic/versions/` with the auto-generated `<hash>_<slug>.py` naming. Don't rename them after creation.
- Always review autogenerated `op.*` calls before committing — Alembic mis-handles enum renames, server defaults, and named constraints.

## Gotchas

- Autogenerate diffs against the live database's current state. Run `alembic upgrade head` first; otherwise the new revision will try to re-create existing tables.
- Constraint names in `__table_args__` are reflected verbatim into migrations; renaming a constraint in models forces a follow-up migration.
